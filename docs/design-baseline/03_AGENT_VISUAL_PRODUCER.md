# Agent 3：Visual Producer（视觉生产与海报合成）

> 版本：v0.1｜日期：2026-09-22｜性质：课程项目设计提案，尚未实现或实测。


[返回主文档](00_PROJECT_OVERVIEW.md) · [上一阶段：Layout Planner](02_AGENT_LAYOUT_PLANNER.md) · [下一阶段：Quality Critic](04_AGENT_QUALITY_CRITIC.md)

## 1. 角色定位

把已经明确的 PosterSpec 变成真实素材和 720 × 1280 PNG。核心不是让模型一次性画完整海报，而是：**生成或复用视觉素材 → 安全处理 → 用程序绘制准确文字与布局 → 保存可审核的候选。**

A3 对素材生产负责，但不拥有主题、正式文案或布局的任意改写权。它发布 `PosterCandidate.status = rendered`，不宣称海报已经通过质量审核。

如果实现只有固定的 `generate_image()` 调用，那只是一个工具包装器，不应夸大为有复杂自主能力的 Agent。A3 的 Agent 决策主要体现在：依据预算与能力选择生成/缓存/重试/报错路径，执行合法返工，处理工具异常。确定的图片处理和渲染仍交给代码完成。

## 2. 职责边界

| 必须负责 | 不负责 |
|---|---|
| 将素材需求适配到真实生图后端 | 擅自改 A1 文案或 A2 坐标/字号 |
| 选择复用缓存还是生成受影响素材 | 为了更好看而无授权重做全局设计 |
| 记录模型、参数、素材来源与处理步骤 | 声称模型一定不产生文字、扭曲或其他瑕疵 |
| 验证图片格式、尺寸、完整性和安全路径 | 根据元数据就断言图片语义正确 |
| 按 Spec 渲染文字、素材与图层 | 让模型生成任意可执行绘图代码 |
| 局部素材返工后重新合成与留痕 | 直接把返回的候选标记为最终通过 |

## 3. 内部架构

```text
PosterSpec + 只读 Brief + 预算 + 可选 RepairPlan
        |
        v
执行决策：哪些素材可复用、哪些需要生成、工具是否支持
        |
        +---- 缓存命中 ------------------------------+
        |                                            |
        v                                            |
生成适配器 → 生图后端 → 原始图片                       |
        |                                            |
        v                                            |
解码/校验 → 明确的裁剪缩放 → 规范化素材 ----------------+
        |
        v
Pillow Renderer：依据 Spec 绘制图片、文字和装饰
        |
        v
PNG + Candidate + RenderManifest + Artifact Index
        |
        v
A4 审核
```

生成器、图片处理器和 renderer 是不同组件。更换生图模型时不应该重写文字排版；修改字号时不应该调用生图模型。

## 4. 工具组成与调用契约

这些接口需要在本项目中实现；不是已存在的第三方同名函数。

| 工具 | 输入 / 输出 | 说明 |
|---|---|---|
| `get_generator_capabilities` | 后端配置 → 支持的尺寸/比例、种子、负面提示、图像编辑能力 | 启动时探测或读取经确认的配置，不能凭模型名称猜能力 |
| `lookup_asset_cache` | 实际生成条件的指纹 → 可用素材及来源 | 检查版本、哈希和语义兼容性 |
| `generate_visual_asset` | GenerationRequest → 图片引用、真实参数与调用用量 | 是付费/高成本工具，调用前由运行时授权预算 |
| `validate_asset_file` | 文件引用 → 解码、尺寸、格式与完整性结果 | 不把 HTTP 200 或文件存在当成有效图像 |
| `prepare_asset` | 原图 + Spec 中的适配规则 → 规范化素材、变换记录 | 保持纵横比；裁剪和缩放要明确留痕 |
| `measure_text_block` | 与 A2 相同的字体和文本参数 → 真实边界 | 用于渲染前复查；不改变正式文案 [T3] |
| `render_poster` | Spec + 受信素材映射 → PNG 与 RenderManifest | 只支持白名单元素，不执行模型代码 |
| `save_artifact` | 工具真实输出 → 文件引用与哈希索引 | 由运行时包装执行，禁止任意路径写入 |
| `edit_visual_asset`（后期可选） | 原素材 + 合法编辑区域/指令 → 新素材版本 | 只有后端能力与坐标映射测试通过后才启用 |

初版可只支持一张主视觉和一次生成。抠图、多素材组合、透明背景与局部编辑是扩展能力，不能在输出里假装已经实现。

## 5. 输入契约

| 输入 | 必要内容 | 约束 |
|---|---|---|
| 当前 PosterSpec | 元素、坐标、asset_plan、render_policy | 必须通过 A2 的结构与文字预检 |
| 当前 CreativeBrief | 原始含义、文案、禁止项 | 只读，用于检查工具适配是否改变意图 |
| 生成后端能力与配置 | 模型实际 ID、支持参数、凭据引用 | 密钥只能来自环境或安全配置，不写进提示词/日志 |
| 当前预算 | 剩余图像操作数和允许动作 | 运行时控制，模型不可自行扩大 |
| 旧素材与 RepairPlan（返工时） | 素材版本、目标 ID、保留范围和问题证据 | 版本匹配；只能修改授权对象 |

### 5.1 GenerationRequest 的内部模板

```json
{
  "run_id": "run_demo_001",
  "asset_id": "hero_image",
  "based_on": {
    "brief_version": 1,
    "spec_version": 1
  },
  "prompt": "平静蓝色海面与开阔天空，连续自然的海平线，简洁摄影感，柔和光线，无人物，无文字，无标志。",
  "negative_prompt": "暴风雨，密集人群，文字，标志，重影海平线",
  "target_size": {
    "width": 648,
    "height": 850
  },
  "seed": null,
  "repair_constraints": [],
  "allow_global_design_change": false
}
```


`target_size` 指最终素材用途；适配器可以选择后端支持的更大尺寸，再按 Spec 处理。`seed` 为 null 表示本次未指定或后端不支持；必须在结果中区分这两种原因。`repair_constraints` 是被批准的局部修复要求，不得覆盖原始语义或正式文案。

上面只是本项目的统一接口。每个 provider 的实际参数名、支持尺寸和编辑能力都需要另写适配器并测试，不能把该 JSON 原样发给任意服务就假设可用。

## 6. 输出模板：PosterCandidate

下方 JSON 是**跨文档一致的说明性输出模板**，不是已运行结果；其中图片路径、检查结论和用量均为演示值。工具名称是本项目拟实现的接口，不是声称第三方库已经提供同名 API。


```json
{
  "schema_version": "0.1.0",
  "run_id": "run_demo_001",
  "candidate_id": "cand_001",
  "status": "rendered",
  "based_on": {
    "brief_version": 1,
    "spec_version": 1
  },
  "poster_ref": "candidates/cand_001/poster.png",
  "render_manifest_ref": "candidates/cand_001/render_manifest.json",
  "artifact_index_ref": "artifacts.json",
  "canvas": {
    "width": 720,
    "height": 1280
  },
  "assets": [
    {
      "asset_id": "hero_image",
      "asset_version": 1,
      "file_ref": "assets/hero_image_v1.png",
      "processed_size": {
        "width": 648,
        "height": 850
      },
      "asset_to_canvas": [
        1,
        0,
        0,
        1,
        36,
        260
      ],
      "cache_hit": false
    }
  ],
  "text_manifest": [
    {
      "element_id": "title",
      "text": "静海之蓝",
      "font_family_key": "noto_sans_sc",
      "font_weight": 700,
      "font_size_px": 72
    },
    {
      "element_id": "subtitle",
      "text": "留一点宁静给自己",
      "font_family_key": "noto_sans_sc",
      "font_weight": 400,
      "font_size_px": 28
    }
  ],
  "usage_delta": {
    "image_ops": 1,
    "render_calls": 1,
    "cache_hits": 0
  },
  "warnings": []
}
```


### 6.1 字段解释

| 字段 | 含义 |
|---|---|
| `status: rendered` | 成功产生候选文件，但未通过 A4 审核 |
| `based_on` | 该图片依赖的 Brief/Spec 版本 |
| `poster_ref` | 实际候选 PNG 的受控路径 |
| `render_manifest_ref` | 详细文字测量、元素边界、实际变换与环境信息 |
| `artifact_index_ref` | 原始/处理后素材、输出文件的哈希与来源索引 |
| `assets` | 稳定素材 ID、版本、处理后尺寸和画布变换 |
| `text_manifest` | 实际传给 renderer 的文字参数；不能替代像素级可读性检查 |
| `usage_delta` | 本阶段真实工具用量的摘要，由包装器生成 |
| `warnings` | 非致命问题；阻塞错误不能只塞进 warning 然后报成功 |

所有 `*_ref` 都相对于 run 根目录解析。示例中的文件不是真实已生成图片；实现时只有在文件存在、可解码且哈希索引落盘后才能发布对应引用。

### 6.2 RenderManifest 至少记录什么

画布实际宽高与颜色模式；每个元素的 Spec box 和真实绘制边界；文本最终行列表、字体文件哈希、字重和字号；素材原始尺寸、处理后尺寸、裁剪框与变换；renderer 与字体配置版本；输出文件哈希、生成时间和警告。

文件哈希保存在 Artifact Index/RenderManifest，不需要把全部哈希重复塞进每个 Agent 的 prompt。任何读取应由 ArtifactStore 检查引用是否属于当前 run。

`asset_to_canvas` 使用 `[a,b,c,d,e,f]` 仿射表示：`x_canvas = a*x_asset + c*y_asset + e`，`y_canvas = b*x_asset + d*y_asset + f`。示例规范化素材已经是 648×850，因此只需要平移到 `(36,260)`。原始生图到规范化素材的裁剪与缩放还需单独记录。

## 7. 实现思路

### 7.1 分开固定策略与模型决策

合法 Spec 的普通绘制走代码，不让 LLM 每次重新决定图层顺序。A3 的决策输入应包括：需要生成的素材列表、可用缓存、后端能力、剩余预算和修复约束。输出执行动作后再由代码校验并调用工具。

对于缓存命中、尺寸不支持、图片损坏、生成失败和素材返工等情况，A3 可以选择允许的下一步；如果只有唯一合法路径，直接使用程序处理，避免为了“增加 Agent 感”额外消耗 token。

### 7.2 素材生成而非整图文字生成

普通主视觉 prompt 明确需要哪些主体、关系、风格和留白，尽量要求无正式文字。生图结果仍可能出现文字或伪文字，因此这只是指导，不是保证。

PosterCraft 是整图海报路线的有价值对照，不应为了证明分层方案更好而弱化其输入。[R6] Qwen-Image 可作为生成/编辑后端候选，但实际支持的能力需按固定版本检测，不能承诺任意蒙版或尺寸都可使用。[T5]

### 7.3 比例适配与素材完整性

选择后端支持且接近目标比例的尺寸，生成后安全解码、处理方向信息，再依据 Spec 的 `fit` 与 `focus_point_norm` 做等比缩放/裁剪。禁止直接拉伸主体来凑 720×1280。

若必须裁掉关键主体才能填满槽位，返回布局或素材适配问题，不能偷偷把 `cover` 改成 `contain` 后假装严格按 Spec 完成。A4 在真实图像上判断主体是否仍完整；边界检查本身无法保证语义完整性。

原始图与处理后素材分开保存，避免多轮裁剪反复损失画质。限制最大解码像素数与文件体积，避免畸形或过大文件拖垮进程。

### 7.4 确定性文字与渲染

初版使用 Pillow ImageDraw，并在同一受控环境中测量和绘制文字。[T3] 渲染器按 Spec 图层顺序执行，在既定位置绘制真实字体，而不是让图片模型画字。

实现明确换行、字形覆盖与字体选择策略。字重必须对应实际字体文件，不能因为请求 `700` 就默认为已有真实粗体。缺字体、缺字形、文字溢出一律报错，不静默替换。

固定字体文件、渲染器版本、输入资产和配置，才有条件追求可重复输出。不能把“程序渲染”理解成“任何操作系统、任何字体版本都逐像素一致”。本次交付只包含 Markdown，不包含任何字体文件；字体资源在实际部署时另行取得并核对许可。

### 7.5 缓存、重试和成本

缓存指纹覆盖真正发给后端的提示、模型/权重、参数、参考资产和预处理配置。标题位置改变不影响主视觉语义，因此应命中缓存。材质、主体或视觉风格改变则应重新生成相关素材。

传输超时和生成质量不佳是两类问题：前者属于工具故障，优先确认请求是否已经完成，防止重复计费；后者必须通过合法质量返工进入下一轮。每个已提交的图像请求都记录，不能只统计拿到成功图片的调用。

提供幂等键或请求 ID 的后端应利用其能力；不支持时明确记录重复请求风险。缺少必要凭据时失败，不替换成一张空白或随机测试图冒充真实生成。

## 8. 局部返工机制

| 修复类型 | A3 做什么 | 不做什么 |
|---|---|---|
| A2 更新字号/位置 | 使用已有素材重新渲染 | 不再次生成主视觉 |
| 主视觉存在扭曲或无关文字 | 在原语义约束下重新生成 `hero_image` 并增加素材版本 | 不改变标题、布局和其他素材 |
| 一个素材文件损坏 | 重取或重做受影响素材，重新校验 | 不重启所有 Agent |
| 元素位置不合适但 Spec 明确如此 | 报给 A2 或执行其新版 Spec | 不自己静默移动元素 |
| 可用的后期局部编辑 | 将画布问题区域映射到素材坐标，调用支持的编辑后端 | 不把画布 bbox 原样当成素材蒙版 |

**MVP 的“局部修复”首先指元素/素材级修复，不承诺像素级 inpainting。** 即使整个主视觉需要重生，标题和排版仍可完全保留。只有编辑后端和坐标逆变换经过测试，才启用小区域编辑。

A3 可以在实际 GenerationRequest 中附加来自 RepairPlan 的修复约束，例如“保持蓝色平静海面，修复双重海平线”。原始 Spec 不由 A3 修改；实际编译后的生成提示和修复来源需要写入素材 provenance。

每个新候选都必须重新交 A4 审核。即使目标问题被修好，也要检查原先正确的关键词、文字和布局有没有退化。

## 9. 建议提示词骨架

```text
你是 Visual Producer。使用给定 Spec、工具能力和预算生产可审核候选。
保持原始语义、正式文案、布局和字体规格；没有授权不能修改它们。
优先复用与当前生成条件一致的素材，只生成缺失或被要求修复的资产。
只调用能力列表中存在的工具与参数，不假设支持任意尺寸、种子或蒙版编辑。
正常主视觉不承担正式文案绘制；所有正式文字由 renderer 按 Spec 绘制。
工具报错必须真实报告；禁止把空白、占位或旧版本文件当作本轮成功结果。
返工只处理指定目标，并保留其他元素。
输出实际候选和证据引用；质量结论交给 Critic，不自行宣称 passed。
```

## 10. 测试与验收

| 测试 | 预期结果 |
|---|---|
| 固定 Spec + 固定素材 + 固定字体环境 | 生成可解码的 720×1280 PNG |
| 中文标题/长英文标题 | 测量与渲染一致；缺字/溢出不被隐瞒 |
| 只修改标题位置 | 图像 API 调用增量为 0，主视觉哈希不变 |
| 只返工主视觉 | 标题文案、字号、坐标不变；新素材有独立版本 |
| 生成器不支持负面提示/任意尺寸 | 显式适配或拒绝，记录实际调用参数 |
| 超时、429、无效图片 | 有限重试或失败；用量记录包含尝试 |
| 达到预算上限 | 不再发起付费请求，返回可解释状态 |
| 路径含 `../`、外部 URL 或脚本 | 被 ArtifactStore/Schema 拒绝 |
| 缓存资产模型版本不匹配 | 不错误命中缓存 |
| 旧 Candidate 重发到审核 | 版本检查识别旧产物，不误当本轮结果 |

真实模型性能用开发样例验证；上述多数工程测试先用 stub 完成。通过这些测试意味着生产链路可靠，不代表所有海报都美观或没有生成瑕疵。

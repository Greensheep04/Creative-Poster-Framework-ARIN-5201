# Creative Poster Generator：项目主设计文档

> 版本：v0.1｜日期：2026-09-22｜性质：课程项目设计提案，尚未实现或实测。


## 1. 文档用途与阅读入口

本项目以 **2–5 个关键词生成一张 720 × 1280 创意海报**。采用四个专职 Agent，将稀疏意图转成结构化设计，再生成视觉素材、程序化合成海报，并通过质量审核进行有预算限制的定向返工。

这套文档供组员讨论、分工和后续编码交接使用，不是已完成实现，也不把设计假设写成实验结论。四个 Agent 是职责隔离的逻辑角色，不是四个人，也不自动意味着四套不同参数的基础模型。

| 文件 | 负责说明 |
|---|---|
| [00_PROJECT_OVERVIEW.md](00_PROJECT_OVERVIEW.md) | 本文：整体体系、共享规则、项目亮点、实验设计和实施顺序 |
| [01_AGENT_CREATIVE_DIRECTOR.md](01_AGENT_CREATIVE_DIRECTOR.md) | Agent 1：关键词理解、语义约束、创意简报与文案 |
| [02_AGENT_LAYOUT_PLANNER.md](02_AGENT_LAYOUT_PLANNER.md) | Agent 2：设计规格、布局、字体、颜色与素材需求 |
| [03_AGENT_VISUAL_PRODUCER.md](03_AGENT_VISUAL_PRODUCER.md) | Agent 3：素材生成、缓存、处理与确定性渲染 |
| [04_AGENT_QUALITY_CRITIC.md](04_AGENT_QUALITY_CRITIC.md) | Agent 4：质量检查、问题归因、定向返工建议 |

**规则优先级：课程硬性要求 > 本文的公共契约 > 各 Agent 的局部实现。** 修改公共字段、职责边界或预算时，要同步修改相关子文档，不能让各模块自行约定不同含义。

## 2. 课程要求与本项目设计的边界

课程来源：用户提供的 `MAIE5421_CourseProject_Guidelines_v3(1).pdf`，封面日期 2026-09-19，Topic 1 位于第 2 页。

| 项目 | 课程原文支持的要求 | 本项目拟采用的实现 |
|---|---|---|
| 输入 | 2–5 个关键词 | 保留原始词条与稳定 keyword_id，不要求用户补成长提示词 |
| 输出 | 720 × 1280 海报图像 | PNG；另保存 JSON、素材和过程记录以支持调试 |
| Agent | Requirements 写明 3–4 个 specialized agents，角色清晰 | 四个逻辑 Agent，不增加第五个 Supervisor Agent |
| 通信 | Robust inter-agent communication | 类型化数据、版本校验、错误码、有限重试与可追溯状态 |
| 结果质量 | 概念理解、视觉生成、布局设计、风格一致性 | 对应语义、图像、文字、布局和风格评测 |
| 质量验证 | 技术指导建议质量、指令遵循、鲁棒性、效率等维度 | 程序检查 + 视觉审核 + 定向返工；具体指标由本项目提出 |

**需要向教师确认的一处措辞：** Project Description 使用了 “3–4 specialized models”，Requirements 使用了 “3–4 specialized agents”。因此不能自行断言“同一个 LLM 分饰四角一定符合全部要求”。建议将四个角色及其实际 LLM/VLM/生图模型映射写入 proposal，确认是否要求不同基础模型。架构本身允许替换模型，不依赖“必须同模型”或“必须四模型”的假设。

课程第 1 页另要求 5–6 人组队、最多 2 页 proposal、6 页 CVPR 格式报告（参考文献不计页数）和约 10 分钟展示，幻灯片不用提交。当前 PDF 未给具体截止日期。以上是课程要求；本项目的输出目录、测试集规模、阈值与技术栈则是设计建议。

## 3. 项目定位与范围

### 3.1 目标

我们不是把关键词简单扩成一段长 prompt，也不主张“目前不存在海报生成方案”。本轮核对到的 PosterCraft 提供文本到海报的生成路线，VibePoster 提供相近的多 Agent 工程系统；Paper2Poster、PosterGen、PosterMELD 则主要面向学术论文海报。[R1][R2][R4][R6][R7]

因此项目定位是：**面向稀疏关键词输入，构建可解释、可编辑中间状态、可定向返工的创意海报系统，并验证这些设计是否改善质量与成本。** 相比“完全从零设计一个生成模型”，更适合以成熟基础模型与工具为基础开展系统实验。

### 3.2 MVP 范围

只做单张静态竖版海报；默认一张主视觉、一个短标题和可选副标题。支持有限的版式与字体注册表。生图模型负责视觉素材，文字与布局通过程序渲染。默认不训练基础模型，不做在线编辑器、用户账号、多轮品牌管理、多海报套系或视频分镜。

RAG、素材检索、多候选设计、局部图像编辑与 SVG 导出属于后续可选扩展，不是初版的先决条件。先验证完整闭环，再决定是否值得增加复杂度。

### 3.3 两条生成路线的取舍

| 路线 | 优势 | 局限 | 项目位置 |
|---|---|---|---|
| 一次性生成整张海报 | 链路短，文字与图像的艺术融合可能更自然 | 元素级修改和准确返工不容易；能力取决于具体模型 | 必须保留的 baseline，而不是预先判定它较差 |
| 素材生成 + 结构化布局 + 程序文字 | 文案和坐标可控，布局问题可以不重生图片 | 自由度受版式限制，图文融合可能显得模板化 | 本项目主路线；效果须由对照实验验证 |

使用程序渲染不是因为“所有生图模型都无法正确生成文字”。PosterCraft、Qwen-Image 等已把文字或图像编辑作为能力方向。[R6][T5] 我们选择分层主要是为了**可控性、局部编辑与实验可归因性**。

## 4. 四个 Agent 的分工与能力

| Agent | 核心能力 | 主要输入 | 主要输出 | 可以决定什么 | 不应该做什么 |
|---|---|---|---|---|---|
| A1 Creative Director | 理解关键词、处理歧义、建立视觉语义约束、生成创意文案 | KeywordRequest；可选设计参考 | CreativeBrief | 主题解释、创意方向、正式文案 | 偷换用户关键词；编造事实性活动信息；指定最终像素布局 |
| A2 Layout Planner | 把意图变成可执行设计规格 | CreativeBrief；画布与字体能力 | PosterSpec | 元素位置、尺寸、层级、字体、精确配色、素材需求 | 擅自改 A1 的文案；生成图片；写任意执行脚本 |
| A3 Visual Producer | 选择工具动作、生成/复用素材、处理并合成海报 | PosterSpec；只读 Brief；有限预算 | PosterCandidate 与渲染清单 | 工具调用、支持的生成参数、素材复用和已授权素材返工 | 随意改标题/布局；偷偷扩大成本；把占位图当成成功结果 |
| A4 Quality Critic | 基于证据判断语义、视觉、文字和布局问题，并归因 | 原始请求、Brief、Spec、实际 PNG 与工具证据 | QAReport + RepairPlan | 报告问题、严重度、证据、建议返工对象 | 直接写入别人的产物；执行修复；靠一个主观总分覆盖硬性错误 |

**A1 管“表达什么”，A2 管“如何摆放和呈现”，A3 管“如何把规格变成真实图像”，A4 管“哪里不符合要求、证据是什么”。**

A2 与 A3 都可能调用文字测量，但使用同一个工具与字体配置；只有 A2 拥有排版规格的语义修改权限。A4 可建议缩短标题，但必须回到 A1 修改文案，再由 A2 重新适配。

## 5. 系统架构与执行链路

```text
KeywordRequest（不可变）
        |
        v
A1 Creative Director ----> CreativeBrief vN
        |
        v
A2 Layout Planner -------> PosterSpec vM
        |                       |
        |                程序预检：schema、字形、边界、文字适配
        v
A3 Visual Producer ------> 素材 / RenderManifest / PosterCandidate
        |                       |
        |                图片模型 + Pillow 渲染工具
        v
A4 Quality Critic -------> QAReport / RepairPlan
        |
        v
程序化 Router / Budget Guard / Version Guard
        |---- pass -----------> 输出 PNG 与过程文件
        |---- repair ---------> A1 / A2 / A3 中的责任方
        |---- 无预算或不确定 ---> needs_review，明确未通过
        |---- 工具无法恢复 ----> failed，记录失败原因
```

Router、Renderer、ArtifactStore、OCR 和 Schema Validator 都是工具或运行时组件，不是额外的 Agent。Graph 中也可以有多个非 Agent 节点，节点数不等于 Agent 数。

建议使用 LangGraph 组织持久化状态与条件转移，但不依赖某个库才能实现：一个清晰的状态机也能完成相同控制逻辑。LangGraph 是编排候选，不替代字段校验、权限或预算逻辑。[T1]

## 6. 共享数据契约

### 6.1 五种核心产物

| 对象 | 业务字段定义位置 | 唯一内容负责人 | 下游用途 |
|---|---|---|---|
| KeywordRequest | A1 文档的输入模板 | 请求入口；运行中不可变 | 所有阶段的最高语义约束 |
| CreativeBrief | A1 文档的输出模板 | A1 | 关键词解释、文案与设计意图 |
| PosterSpec | A2 文档的输出模板 | A2 | 可执行的画布、元素和素材计划 |
| PosterCandidate | A3 文档的输出模板 | A3 | 实际图片、素材引用、渲染证据 |
| QAReport / RepairPlan | A4 文档的输出模板 | A4 提案；Router 校验 | 放行、返工或人工复核 |

所有示例统一使用 `schema_version: "0.1.0"`、`run_id: "run_demo_001"`。示例不是已生成海报或已获得的评测结果。

### 6.2 不可破坏的公共约束

1. **原始意图不可变。** `keywords` 的文本和 ID 由入口保存，后续阶段不能删除或替换。创意解释可以调整，但必须仍可追溯到原始词条。
2. **按版本消费。** Brief、Spec、Candidate 和 QA 必须记录依赖版本。旧版本报告不得直接修复新版本产物。
3. **坐标统一。** 画布左上角为原点，x 向右、y 向下，单位为最终 720 × 1280 PNG 的像素；`box` 一律是 `x/y/width/height`。规范化坐标仅用于名称带 `_norm` 的字段。
4. **资源通过引用传递。** 路径相对于当前 run 根目录解析，不能从模型输出任意绝对路径、外部 URL 或 `../` 读取资源。图像原始字节不进入冗长对话历史。
5. **职责隔离。** 文案归 A1，布局归 A2，素材归 A3。A4 只有审核与提案权。所有持久化写入由运行时执行并记录。
6. **字段校验不是语义保证。** JSON 合法只意味着结构通过；关键词是否真正在画面体现，仍需视觉审核。
7. **模型输出不等于可执行程序。** 工具只接受受限参数；拒绝模型提供的 shell、Python、JavaScript、任意 SVG/HTML 脚本。

建议用 Pydantic 定义类型、枚举与跨字段校验，并由这些类型导出 JSON Schema。[T2] 当前文档中的 JSON 是业务模板，不是已经生成的完整 JSON Schema 实现。

  "status": "running",
  "request_ref": "request.json",
  "current": {

### 6.4 运行目录建议

```text
runs/<run_id>/
  request.json
  effective_config.json
  brief_v1.json
  spec_v1.json
  artifacts.json
  assets/
  candidates/cand_001/
    candidate.json
    poster.png
    render_manifest.json
    qa_report.json
    qa/
  events.jsonl
  final_result.json
```

`artifacts.json` 保存文件哈希、来源与版本；原始模型响应、实际模型标识、请求参数、字体/渲染器版本、随机种子支持情况和提示词版本应进入审计记录。复现实验依赖这些记录，不能只保存最后一张 PNG。

### 6.5 统一错误与事件约定

成功时发布对应业务产物；失败时返回共同的 StageError，不把半成品当成成功 Brief/Spec/Candidate。说明性格式如下：

```json
{
  "schema_version": "0.1.0",
  "run_id": "run_demo_001",
  "stage": "visual_producer",
  "status": "error",
  "based_on": {"brief_version": 1, "spec_version": 1},
  "error": {
    "code": "PROVIDER_UNAVAILABLE",
    "retryable": true,
    "message": "生图后端暂时不可用。",
    "affected_ids": ["hero_image"]
  }
}
```

初版错误码建议包括 `INVALID_INPUT`、`SCHEMA_INVALID`、`STALE_VERSION`、`MISSING_FONT`、`TEXT_OVERFLOW`、`MISSING_ASSET`、`PROVIDER_UNAVAILABLE`、`BUDGET_EXHAUSTED` 和 `CONSTRAINT_CONFLICT`。A1 尚未形成版本时，`based_on` 可以为 null。

`retryable` 只是工具对故障性质的描述，不是自动重试授权。运行时仍需确认预算、版本和幂等性；配置错误与用户约束冲突不能靠重复调用模型解决。每次阶段开始/结束、工具请求、产物更新、修复批准/拒绝，都写入含 run_id、阶段、版本和关联请求 ID 的事件记录；不得记录密钥。

## 7. 定向返工：归因、权限与终止

### 7.1 按最早出现错误的位置归因

| 现象与证据 | 路由 | 允许修改 | 必须保护 |
|---|---|---|---|
| Brief 已漏掉关键词或误解用户意图 | A1 | 语义解释与创意方向，必要时文案 | 原始请求 |
| Brief 正确，Spec 漏安排对应主视觉/元素 | A2 | 版式、元素或素材计划 | 原始意图、未授权文案 |
| Brief 与 Spec 正确，实际图像没有生成所需主体 | A3 | 对应素材；必要时修复提示附加约束 | 布局、文案、其他素材 |
| 字号/位置造成溢出、遮挡或阅读层级问题 | A2，再交 A3 渲染 | 指定元素样式与几何 | 正式文案与可复用图片 |
| 规格正确但渲染器缺字、字体不可用或文件损坏 | 工具错误处理；必要时 A3 | 环境/工具配置或重新执行 | 不允许为了“通过”偷偷更换文案 |
| 图像局部扭曲、重影、无关文字 | A3 | 对应素材 | 没有问题的文字与布局 |

“画面没有海洋”不能机械地一律回 A1：先判断 Brief、Spec、生成图哪一层最先出错。A4 返回证据，Router 检查建议是否属于允许动作。

### 7.2 依赖失效与缓存

A1 更新 Brief 后，旧 Spec 和 Candidate 变为过期，必须重新确认；A2 更新 Spec 后，旧 Candidate 过期，但**没有改变生成条件的素材可以复用**；A3 只更新一张素材时，其他素材保留，重新合成并审核新 Candidate。整个图中不允许旧 QA 报告放行新图。

素材缓存键应包含模型/权重版本、生成提示、负面提示的实际支持情况、尺寸/比例、种子、输入参考图哈希和预处理参数。单纯移动标题不应使主视觉缓存失效；更改主视觉语义则必须失效。

### 7.3 初版预算与结果状态

建议起点是**初次生成后最多 2 轮质量返工**，每次只处理一个返工计划。最多 3 次图像生成/编辑请求，最多 3 次 Critic 视觉审核。Schema 修复最多重试 1 次；所有实际远程调用仍需计入用量。上述数字是开发集待校准的默认值，不是论文结论。

不要把“同一个错误未改变”当作继续无限循环的理由。发现重复失败、不可满足的输入或核心证据不确定，应终止为 `needs_review`。发生无法恢复的工具错误为 `failed`，不输出冒充成功的占位海报。

`passed` 需要满足硬性输入输出要求、无阻塞问题、每个必需关键词有可接受证据、关键检查不为 unknown。视觉软指标的初始放行线可暂定为每项至少 3/5，但必须在开发集校准并固定，不能宣称 3/5 就客观代表高质量。无需用一个加权总分掩盖严重拼写或语义错误。

## 8. 技术选型与实现边界

| 层 | 初版建议 | 选择理由与边界 |
|---|---|---|
| 编排 | LangGraph 或等价显式状态机 | 四个 Agent 节点 + 程序检查/路由；不建自治聊天群 [T1] |
| 结构契约 | Pydantic + JSON Schema | 支持强类型、枚举、长度与引用校验 [T2] |
| 模型 | 支持结构化输出的 LLM、能看图的 VLM、一个生图后端 | 型号由小规模可行性测试决定；记录版本，不承诺特定产品效果 |
| 生成适配 | 自定义 ImageGenerator 接口 | 屏蔽尺寸、负面提示、种子、编辑能力的差异；Qwen-Image 是可研究候选之一 [T5] |
| 主渲染器 | Pillow + 受控字体注册表 | 同一引擎测量和绘制文字，稳定输出 PNG；不是让 LLM 写任意绘图代码 [T3] |
| 质量工具 | 几何/字形/元数据检查 + VLM；OCR 按需 | OCR 用于像素文字识别或疑点核查，不是额外 Agent，也不能被当作绝对真值 [T4] |
| 存储与追踪 | 本地 run 目录 + JSONL 事件 | 先保证重放与实验记录；暂不需要数据库或服务集群 |
| 参考检索 | 初版可关闭；后续加入有来源的本地设计案例库 | 不为“看起来像 Agent”强加 RAG、知识图谱或 MCP |

主路线先固定一个渲染引擎。SVG/HTML/PPTX 都是后续替代实现，不要第一版同时维护四套 renderer。文字大小、字体、行距和图层必须来自 Spec；如果实际环境不支持，返回明确错误而不是静默降级。

模型选型可使用 12 组开发样例检查：结构化输出稳定性、中文文案、指令遵循、主体一致性、图像审核能力、费用与延迟。只有能力探测完成后才固定模型配置；本轮没有部署或复现这些模型。

## 9. 可以突出什么：贡献候选与可验证假设

| 候选亮点 | 实际设计 | 对应待验证假设 |
|---|---|---|
| 稀疏意图的可追溯性 | keyword → interpretation → element → visual evidence | 结构化约束能减少关键词在多阶段中丢失 |
| 语义与渲染解耦 | CreativeBrief → PosterSpec → assets + 程序文字 | 相比整图生成，提高文字准确性和局部可编辑性，但可能牺牲部分艺术融合 |
| 定向返工 | 带 target、版本、证据和允许动作的 RepairPlan | 相比全量重做，用更少图像调用修复错误，并减少无关区域退化 |
| 可评估的工程闭环 | 规则检查与视觉检查分离；完整记录失败和成本 | 能说明系统何时有效、何时失败，而不只是展示成功样例 |

**不把“四个 Agent”“用了 JSON”“加入 Critic”单独写成全新研究贡献。** 相近思想已出现在相关工作中。[R1][R3][R4][R5][R7] 报告应明确借鉴部分与本项目新增的任务适配、实现和实验分析；是否有性能提升由数据决定。

## 10. 对比实验设计

### 10.1 研究问题

RQ1：从原始关键词生成结构化 Brief，是否改善语义覆盖？

RQ2：图像素材与程序文字分离，是否改善文字准确性和可编辑性，是否损失美学质量？

RQ3：Critic 的增益是否超过额外成本？定向返工是否优于全量返工？

RQ4：四角色隔离是否比共享所有工具的单 Agent 更可靠，还是主要增益来自结构化契约和工具？

### 10.2 主实验组

| ID | 方法 | 流程 | 主要解释的变量 |
|---|---|---|---|
| B0 | 原始关键词整图生成 | keywords → 生图模型 → 整张海报 | 最低复杂度参照，不预设它一定差 |
| B1 | 扩展后整图生成 | A1 Brief → 同一生图后端 → 整张海报 | 关键词扩展的增益 |
| B2 | 分层生成，无 Critic | A1 → A2 → A3 | 结构化布局与确定性文字的增益 |
| B3 | 分层生成 + 全量返工 | B2 + A4；失败后从 A1 起重新规划/生成 | 审核闭环与全量重试参照 |
| B4 | 分层生成 + 定向返工 | 本项目完整方案 | 错误归因、缓存和局部修改的增益 |
| B5（扩展） | 单 Agent + 同样工具和契约 | 一名逻辑 Agent 完成规划/生产/审核 | 控制“工具更强”后分析职责拆分是否必要 |

B3 的“全量”是当前关键词和配置不变，但重新执行规划与素材生成；不人为继承 B4 的缓存优势。比较时记录真实差异，不把更低实际调用量等同于“相同计算量”。

外部参照可优先考察 PosterCraft 和 VibePoster；只有环境跑通、接口适配和资源允许后才加入正式实验。[R6][R7] Paper2Poster 的输入是论文，不能假装其原任务和关键词创意海报相同；任何改造版都要注明适配方法，不能用不同任务上的公开论文分数横向比较。[R1]

### 10.3 测试集与公平性

建议先做 **12 组开发关键词**，用于排查接口与校准阈值；再准备不重叠的 **60 组测试关键词**，分为具体主体、抽象情绪、关系组合、风格组合和困难/歧义组合五类，每类 12 组。每组仍保持 2–5 个词条。不可满足的矛盾输入另设鲁棒性子集，不与正常生成质量混为一谈。

主实验每组使用 2 次独立运行；若完成 B0–B4，共 600 个运行请求，不包括返工产生的中间图片。预算不足时预先缩减测试规模或方法数，并如实说明；不要做完后只挑成功或好看的样例。

B0 也应获得共同的最小任务说明，例如“生成竖版创意海报”，而不是故意不给模型说明目标。B0/B1 同样使用事先固定的画布比例与等比导出规则；后端不支持精确输出尺寸时，不得用直接拉伸或随意裁掉标题的方式人为削弱 baseline。

相同方法比较尽量固定基础生图模型、配置、画布与评审协议。种子只有在同模型和同后端支持时才有控制意义；跨模型的相同数字种子不代表同等随机性。无法固定时记录为不支持，并使用独立重复运行。

分两种方式报告成本：一是各方法自然运行的真实质量与成本；二是在相同的图像调用上限、VLM 审核上限和明确 token/时间限制下报告质量—成本曲线。**上限相同不等于实际成本相同。** 所有候选、失败请求、传输重试和缓存命中均要记录。

### 10.4 评价指标

| 维度 | 建议测法 | 必须避免的误区 |
|---|---|---|
| 关键词忠实度 | 逐词条标注可见/可感知证据；计算覆盖率与“全部关键词满足”比例 | 不能只因为标题出现了关键词就判定画面满足；抽象词需要预先定义评价说明 |
| 文字正确性 | 在提供固定目标文案的受控子实验中计算字符错误率 CER、完整字符串匹配；同时做人工可读性检查 | 关键词任务没有固定标题真值时，不能强行计算对某个任意标题的 CER |
| 几何合规 | 尺寸、越界、文字适配、缺字、非预期遮挡的通过率 | 图层有意重叠不是错误，必须依据 Spec 判断 |
| 视觉与美学 | 匿名人工 1–5 分或成对偏好；按整体、文字、布局、风格分别评价 | 不只用生成系统自己的 Critic 给自己打分 |
| 返工效果 | 首次通过率、最终通过率、单次修复成功率、错误类型分布 | 一张图修好一个问题但引入其他严重问题，不能算完全修复成功 |
| 修改稳定性 | 未授权字段/素材哈希是否改变；人工查看无关区域是否退化 | 大范围重新生成后“整体还好看”不等于局部修改成功 |
| 运行效率 | 图像/VLM 调用数、token、延迟、实际或可追溯估算费用 | 不隐藏失败、重试或检索带来的成本 |

词条覆盖率按每个样例满足的词条数除以原始词条数计算，再按请求汇总；没有输出的请求计为生成失败，而不是从分母中删除。自动通过率与独立人工质量评价分开报告。

**文字实验必须单独控制。** 端到端关键词实验允许系统自行创作文案，因此没有统一的“正确标题”。为了隔离 renderer 的作用，再准备共享的 Brief 与固定短文案，让整图生成和分层生成使用相同内容。这个子实验是实验控制条件，不是要求正式用户额外输入长文案。

人工评审建议每个被评样例至少两名评审独立判断，争议由第三名复核；方法名隐藏、顺序随机、允许平局。大规模先用独立 VLM 辅助，人工抽样验证一致性。若资源允许，按关键词组聚类 bootstrap 置信区间，避免将同一关键词的重复种子当成完全独立任务。

### 10.5 消融与失败分析

优先做三项：关闭 keyword bindings；将定向返工改为全量返工；关闭几何/文字预检只保留 VLM。分别观察语义遗漏、修改成本和结构性错误。RAG、多候选、局部图像编辑应在基础链路稳定后作为扩展消融，不要一次叠加后无法归因。

另外建立可控故障集：标题越界、必需元素丢失、错误 Brief、损坏图片、字体缺字和过期 RepairPlan。已知注入位置可用来检查 A4 的归因是否正确；它不能代替真实生成结果的端到端评价。

## 11. 测试、实施顺序与验收

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| M0：契约与渲染 | 类型定义、固定示例 Brief/Spec、假素材、PNG renderer | 无模型也能跑通尺寸、中文文字、版本和错误检查 |
| M1：前向生成 | A1、A2、A3 + 一个生图后端 | 2–5 个关键词能产生真实候选海报；失败不伪装成功 |
| M2：审核 | A4 + 规则/VLM 证据，先报告但不自动修复 | 能区分规划错、布局错、素材错和工具错 |
| M3：定向返工 | Router、缓存、预算、依赖失效与终止 | 标题布局返工不调用生图；过期修复不能覆盖新版本 |
| M4：对照实验 | 固定测试集、B0–B4、成本记录、失败样例 | 结果可复查；开发与测试隔离；不把主观判断写成已证实提升 |
| M5：课程交付 | proposal/报告/展示与成员贡献记录 | 按课程格式说明方法、时间线、实验与局限 |

单元测试使用 stub/mock，覆盖非法输入、非法 JSON、引用缺失、文字溢出、工具失败、缓存和路由。集成测试验证四份业务产物的字段一致性。真实模型测试与离线测试分开运行，避免每次代码修改都产生远程费用。

建议项目目录为 `agents/`、`schemas/`、`tools/`、`workflow/`、`prompts/`、`evaluation/` 和 `tests/`。这是后续实现的组织建议，不表示这些代码已经存在。四个 Agent 不等于只能四人分工，5–6 人团队还需明确编排/渲染、评测与集成的实质责任。

## 12. 关键风险与初版控制

| 风险 | 控制方式 |
|---|---|
| 关键词扩展过度发挥 | 原词不可变，逐词条绑定；所有新增非事实设定标为假设 |
| LLM 只会写模糊布局描述 | 强制 PosterSpec；真实文字测量；不接受“放在上方”作为最终规格 |
| 生图模型不支持请求尺寸/编辑/负面提示 | 启动时检测能力；显式适配；不调用不存在的 API |
| 程序渲染显得模板化 | 保留整图 baseline；比较真实美学而不是预设主路线获胜 |
| Critic 误判或自我强化 | 原始请求独立校验、证据裁剪、有限循环、人工与独立评审 |
| 修复导致其他内容退化 | 元素与资产版本锁定，最小修改范围，重新审核全部关键约束 |
| 外部参考图/仓库不可直接复用 | 记录来源和许可；无许可素材不直接合成；开源不等于无使用限制 |
| 不可信内容被当指令 | 参考资料、OCR 和图片文字均视为数据，不得覆盖系统规则或执行代码 |
